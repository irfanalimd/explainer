Virtual memory: How each program gets its own addresses, and how one read finds its byte
level core · 3 stories · 3 knobs (Address the program reads, Or type your own address (hex), Sticky notes (TLB size))

HOOK      Two programs can use the same memory address for their own data. Why don't they overwrite
          each other, and how is it fast?
GOAL      Turn a program's own address into a real place in memory, so programs stay apart and reads
          stay fast.
OBJECTIVES
  o-split: Perform the split of an address into its page number, which is looked up, and its offset,
           which copies straight over.
  o-walk: Explain how four groups of 9 bits each pick one line in a chain of four tables, starting
          from CR3.
  o-cost: Compare a sticky-note hit with a directory walk, and compute the average cost of many
          reads in one page.
  o-apart: Explain why two programs reading the same address reach different rooms.
  o-fault: Predict what happens when a page is out on disk, in order, and which part costs the most.
PICTURE   a building where each program has its own apartment numbers
  number  an apartment number  =  a virtual address: the program's own number  (virtual address)
  spot    the spot inside the apartment  =  the offset, the low 12 bits  (offset)
  directorythe program's building directory  =  its page table  (page table)
  desk    which directory lies open on the desk  =  CR3, where that page table starts  (CR3)
  room    the real room  =  a frame of physical memory  (frame)
  notes   the receptionist's sticky notes  =  the TLB  (TLB)
  storage a room whose boxes went to storage  =  a page out on disk: a page fault  (page fault)
  breaks  A receptionist reads one big directory. The CPU's is four small tables, each saying where
          the next starts, and it keeps only a few notes.
BELIEFS
  m-walk: “Every read looks its address up in the directory, so every read is slow.” Only a miss
          reads the directory. The note it leaves answers every later read in that page in one
          cycle.
  m-fixed: “An address is one fixed place in memory, the same for every program.” An address is the
           program's own number. Its directory decides which real room it means.
  m-unique: “Two programs can't use the same address: the system gives each its own addresses.”
            Programs use the same addresses all the time. Their directories send them to different
            rooms.
  m-note: “Once the kernel brings the page back, the sticky notes know about it too.” The kernel
          fixes the directory line, not the notes. A note is written only after a walk that finds
          the room.
WORDS
  virtual address: (the program's own address) The number a program uses for a place in its memory:
                   its own apartment number, not a real room.
  page: (a 4,096-byte block) A block of 4,096 bytes. Memory is handed out, looked up and moved one
        block at a time.
  offset: (the place inside the block) How many bytes into its 4,096-byte block a byte sits,
          counting from the block's start.
  TLB: (the sticky notes) Translation lookaside buffer: the CPU's few sticky notes of recently
       looked-up pages and their real rooms.
  cycle: (one clock tick) One tick of the CPU's clock. A 3 GHz CPU ticks 3 billion times a second.
  page table: (the directory) A program's directory: for each of its pages, a line saying which real
              room holds it.
  CR3: (where the directory starts) A slot inside the CPU that holds where the running program's
       directory starts in memory.
  frame: (a real room) A page-sized room of real memory. A page lives in one while it is in memory.
  physical address: (the real address) The real place in memory: the room's start plus the offset
                    inside it.
  page fault: (the page isn't here) The CPU finds a page is not in memory, stops, and asks the
              operating system to fetch it.
  kernel: (the operating system's core) The core of the operating system: it hands out memory and
          fetches pages back from disk.
  cache: (fast memory beside the CPU) Small, fast memory beside the CPU that keeps copies of
         recently read memory, so reading again is cheap.

   0  ★ The program reads one byte at `0x7f3a_2c10_8e48`. That is its own virtual address. [virtual
      address: The number a program uses for a place in its memory: its own apartment number, not
      a real room.]   ‹address.read›
        why       If it were a real place, two programs using this number would overwrite each

        look      va
        picture   an apartment number = a virtual address: the program's own number
        · how     Every address a program ever sees, from a printed pointer to its stack, is
                  virtual. The CPU translates it on every read, write and instruction fetch.
        · edge    Only 48 of the 64 bits count: bits 63–48 must copy bit 47, or the CPU refuses the
                  address. Programs live in the lower half, below 0x8000_0000_0000.
        · source  Intel SDM 2025, Vol. 1, §3.3.7.1, canonical addressing
   1  ★ The low 12 bits, `0xe48`, are the offset: the byte's place in its block. [offset: How many
      bytes into its 4,096-byte block a byte sits, counting from the block's start.]   ‹address.offset›
        why       They copy straight down into the real address, unchanged: nothing needs looking
                  up.
        look      pa
        picture   the spot inside the apartment = the offset, the low 12 bits
        · how     12 bits count from 0 to 4,095: one number for each byte of a 4,096-byte block. In
                  hex that is the last 3 digits, here `0xe48`.
        · code    `off = va & 0xfff;` (line 3)
        · source  OSTEP 2023, ch. 18
   2  ★ The upper 36 bits, `0x7f3a2c108`, name its page. Only this part is looked up. [page: A block
      of 4,096 bytes. Memory is handed out, looked up and moved one block at a time.]   ‹address.page›
        why       One lookup for a whole page of 4,096 bytes, not one per byte, keeps the directory
                  small.
        look      va
        picture   an apartment number = a virtual address: the program's own number
        · cost    Translation works per page: 2^36 possible pages to describe, not 2^48 single
                  bytes.
        · how     Bits 47–12 are the page number: `0x7f3a2c108` is `0x7f3a_2c10_8e48` with its last
                  3 hex digits dropped.
        · code    `vpn = va >> 12;` (line 3)

   ▸ Chapter 2 of 6 · Sticky notes
     about     Reading the directory is slow, because it sits in memory too. So the CPU keeps sticky
               notes of recent lookups, the TLB, and checks them first, in one cycle. [TLB:
               Translation lookaside buffer: the CPU's few sticky notes of recently looked-up pages
               and their real rooms.] [cycle: One tick of the CPU's clock. A 3 GHz CPU ticks 3
               billion times a second.]
     so far    Only the page number, `0x7f3a2c108`, needs looking up. But the directory sits in slow
               memory.
     now       Check the CPU's sticky notes for this page first.
     done when The notes answer at once: a hit or a miss.
   3  ★ The TLB checks all 8 notes at once for page `0x7f3a2c108`: a miss.   ‹notes.miss›
        why       No note has this page yet, so the CPU must find its room the slow way.
        look      tlb
        picture   the receptionist's sticky notes = the TLB
        · cost    1 cycle, hit or miss: every note is compared at the same moment.
        · how     Each note pairs a page number with a room number. The TLB compares `0x7f3a2c108`
                  with all 8 page numbers in parallel; a match is a hit.
        · real    Real CPUs keep two levels of notes: a first level of a few dozen, checked in
                  parallel like these, then a bigger second level that costs a few cycles more.
        · source  Drepper 2007, §3.3.1 and §4.3; OSTEP 2023, ch. 19

   ▸ Chapter 3 of 6 · The directory
     about     On a miss, the CPU reads this program's directory, the page table: four small tables
               in a chain. Each 9 bits of the page number pick one line in one table. [page table: A
               program's directory: for each of its pages, a line saying which real room holds it.]
     so far    No note has page `0x7f3a2c108`, so the notes can't say where it lives.
     now       Read the program's directory, one table after another.
     done when The last table's line names the page's room.
   4  ★ The CPU opens this program's directory. CR3 says where it starts: `0x7ae0_d000`. [CR3: A
      slot inside the CPU that holds where the running program's directory starts in memory.]   ‹walk.cr3›
        why       Each program has its own directory, and CR3 picks which one the CPU reads.
        look      cr3
        picture   which directory lies open on the desk = CR3, where that page table starts
        · how     CR3 holds the start of the first table (Intel calls it the PML4); its low 12 bits
                  hold flags, so the CPU masks them off.
        · code    `u64 table = cr3 & ~0xfffull;` (line 6)
        · edge    Only the operating system may write CR3. A program that tries is stopped by the
                  CPU, so it can never point the CPU at another program's directory.
        · source  Intel SDM 2025, Vol. 3A, ch. 4, Paging
   5  Bits 47–39 pick line 254 of the first table, which leads to the second.   ‹walk.level›
        why       Each line says where the next table starts, so the four reads must go one after
                  another.
        look      t0.e1
        picture   the program's building directory = its page table
        · cost    240 cycles: the line comes from main memory, the slow way.
        · how     Each table has 512 lines of 8 bytes. 9 bits count from 0 to 511, so bits 47–39
                  pick line 254, read at the table's start + 8 × 254.
        · code    `u64 e = read64(table + 8 * i);` (line 9)
        · edge    Real CPUs keep recently used upper lines in small paging-structure caches, so a
                  walk to a nearby page may read only the last table. This run keeps none: the worst
                  case.
        · source  Intel SDM 2025, Vol. 3A, ch. 4, Paging
   6  Bits 38–30 pick line 232 of the second table, which leads to the third.   ‹walk.level›
        look      t1.e1
   7  Bits 29–21 pick line 352 of the third table, which leads to the last.   ‹walk.level›
        look      t2.e1
   8  ★ Bits 20–12 pick line 264 of the last table: the page's room, frame `0x189f3`. [frame: A
      page-sized room of real memory. A page lives in one while it is in memory.]   ‹walk.leaf›
        why       This line holds the answer: the real room where page `0x7f3a2c108` lives right
                  now.
        look      t3.e1
        picture   the real room = a frame of physical memory
        · cost    4 lines, each read from main memory at 240 cycles: the walk is 4 reads one after
                  another.
        · how     The line is a real x86-64 entry: the frame number sits in bits 51–12, and the low
                  bits are flags: P (present), RW (may write), US (programs may use it), A
                  (accessed), D (dirty), and NX (no running code from it) in bit 63.
        · edge    The CPU sets the A flag in each line it walks through, and D on a write. The
                  operating system reads A later to pick pages to move out.
        · real    Under a virtual machine each table read is itself translated through the host's
                  tables: up to 24 memory reads for one miss.
        · source  Bhargava et al. 2008

   ▸ Chapter 4 of 6 · The real room
     about     The walk found the page's room. The CPU puts the offset after the room number to get
               the real address, writes a sticky note for next time, and reads the byte.
     so far    Four slow reads later, the last table named the page's room.
     now       Put the offset after the room number, and read the byte.
     done when The real address fills in, a note remembers the room, and the byte lights up.
   9  ★ Room `0x189f3`, then offset `0xe48`: the real address, the physical address, `0x189f_3e48`.
      [physical address: The real place in memory: the room's start plus the offset inside it.]   ‹room.address›
        why       Only the room number came from the directory; the offset copied over unchanged.
        look      pa
        picture   the real room = a frame of physical memory
        · how     The frame number fills bits 38–12 of the physical address and the offset bits
                  11–0: frame × 4,096 + offset. This CPU has 39 physical address bits, a common
                  laptop size.
        · code    `return table | off;` (line 15)
        · source  Intel SDM 2025, Vol. 3A, ch. 4, Paging
  10  ★ A sticky note now maps page `0x7f3a2c108` to room `0x189f3`, replacing `0x7f3a2c3e6`'s note.   ‹room.fill›
        why       The next read in this page can skip the directory entirely.
        look      tlb.v0, tlb.p0
        picture   the receptionist's sticky notes = the TLB
        · how     With every note in use, the one used longest ago makes room: least recently used,
                  LRU.
        · code    `tlb_insert(vpn, table >> 12);` (line 14)
        · edge    A note is written only after a walk that ends in a room. A walk that finds “not
                  present” leaves no note behind.
        · source  Intel SDM 2025, Vol. 3A, ch. 4, Paging
  11  The byte at `0x189f_3e48` is `0x37`. Finding its room cost 961 cycles.   ‹room.byte›
        why       Nothing was remembered, so every directory line came from slow memory: the worst
                  case.
        look      page.b1
        · cost    961 cycles: 1 for the note check, then 4 directory reads at 240 each.
        · source  Drepper 2007, §3.3 and §4

              A) 961 cycles again: every read walks the directory
                 → If you thought every read walks the directory: only a miss does. The note written
                   a moment ago maps page `0x7f3a2c108` to room `0x189f3`, so this read takes 1 cycle.
                   [m-walk]
              B) 1 cycle: a sticky note has this page   ✓
                 → Right. Both bytes are in page `0x7f3a2c108`, and a note already maps it to room
                   `0x189f3`: 1 cycle, no directory.
              C) About half: part of the walk is remembered
                 → Real CPUs do keep some upper directory lines in small caches, which can shorten a
                   walk. But here the note answers first, for the whole page, so no walk starts at
                   all: 1 cycle, not 961. [m-walk]

                   maps that page to its room.
  13  ★ A note has page `0x7f3a2c108`: room `0x189f3` in 1 cycle, no directory read.   ‹again.hit›
        why       One slow lookup per page, then every later read in that page rides on the note.
        look      tlb.v0, tlb.p0
        picture   the receptionist's sticky notes = the TLB
        · cost    1 cycle, against 961 for the first byte.
        · how     A first-level hit is close to free: the CPU's first cache (L1, the smallest copy
                  of memory beside it) starts its lookup with the 12 offset bits, which need no
                  translating, while the TLB translates the rest at the same time.
        · edge    That trick caps the L1 cache: each of its ways can hold at most one 4 KiB page's
                  worth. So a 32 KiB L1 has 8 ways and a 48 KiB one has 12.
        · source  Drepper 2007, §3.3 and §4
  14  Room `0x189f3`, then offset `0xe49`: physical address `0x189f_3e49`, no directory opened.   ‹again.address›
        look      pa

        look      page.b2
  16  It reads on to the page's end: 438 more bytes, 1 cycle each.   ‹again.rest›

  17  ★ 440 reads, 1 400 cycles: about 3.2 each. The note did nearly all the work.   ‹again.total›
        why       The one slow lookup is shared by every read in the page, so the average stays
                  small.
        look      tlb
        · cost    961 cycles for the first read, then 1 for each of the rest: 1 400 cycles over 440
                  reads.
        · edge    Reading one byte from each of 4,096 different pages instead would miss 4,096 times
                  and pay a walk for each. Code that hops across a huge array feels this.
        · real    A 2 MiB huge page lets one note cover 512 small pages, and its walk stops at the
                  third table. Linux uses them for large memory areas.
        · source  Linux docs, transparent hugepages

     about     The operating system now runs program B, which uses the same address through its own

               small number for a recent program instead.
     so far    Program A found its room and noted it. But program B may use the same address.
     now       Switch to program B, and read `0x7f3a_2c10_8e48` there.

  18  ★ Switching to program B, the operating system loads B's directory into CR3: `0x1ab1_2000`.   ‹other.switch›
        why       On this CPU, writing CR3 also wipes every sticky note, since A's notes would
                  mislead B.
        look      cr3
        picture   which directory lies open on the desk = CR3, where that page table starts
        · cost    The wipe is the hidden cost of a switch: B's first reads all miss and walk.
        · how     With PCIDs (process-context identifiers), CR3 carries a 12-bit tag, each note
                  keeps the tag of the program that made it, and a switch keeps other tags' notes.
                  Without them, a CR3 write drops every note except global ones, which the operating
                  system uses for its own pages.
        · real    Linux does not give each process a lasting tag: each CPU recycles 6 tags
                  (TLB_NR_DYN_ASIDS) among the programs it ran most recently, and with page-table
                  isolation each uses a pair, one for the program and one for the operating system
                  side. ARM and RISC-V tag notes the same way (an ASID).
        · source  Linux tlbflush.h TLB_NR_DYN_ASIDS
  19  Program B reads the same address, `0x7f3a_2c10_8e48`. No note has it: a miss.   ‹other.miss›
        look      tlb
     PREDICT  B uses the same address as A. Whose byte will B read?
              A) A's byte: an address is one fixed place in memory
                 → If you thought an address is one fixed place: it is only B's own number. B's
                   directory turns `0x7f3a_2c10_8e48` into room `0xe2b9d`, a room A never uses.
                   [m-fixed]
              B) Its own byte: B's directory points to another room   ✓
                 → Right. CR3 now points at B's directory, and its lines lead `0x7f3a_2c10_8e48` to
                   room `0xe2b9d`, a room only B was given.
              C) Neither: two programs can't share an address
                 → If you thought two programs can't share an address: they share them all the time.
                   B reads `0x7f3a_2c10_8e48`, the same number A read, and its own directory sends it
                   to room `0xe2b9d`. [m-unique]
              why: Every program has its own directory. B's lines lead to a room the operating
                   system gave B, so A's room is never reached.
  20  ★ B's own directory leads `0x7f3a_2c10_8e48` to room `0xe2b9d`, after 960 cycles.   ‹other.walk›
        why       B's CR3 starts a different chain of tables, so the same bits pick lines in other

        look      t0, t1, t2, t3
        picture   the program's building directory = its page table
        · cost    4 reads, 960 cycles: the wipe made B start with no notes.
        · how     The 4 line numbers are the same as A's, because `0x7f3a_2c10_8e48` has not
                  changed. Only the tables they index differ, because the chain starts from B's CR3.
        · edge    Two directories may name the same room on purpose: that is how programs share
                  library code (marked read-only) and shared memory.
        · source  OSTEP 2023, ch. 20

        look      tlb.v0, tlb.p0

  24  ★ Same address, two rooms: each program's directory keeps their data apart.   ‹other.apart›
        why       A program reaches only rooms its own directory names, and only the operating
                  system writes directories.
        look      page, pageB
        picture   the program's building directory = its page table
        · how     Each line also has a US flag (programs may use it) and RW (may write). The
                  operating system's own pages sit in every directory but are marked off-limits to
                  programs.
        · real    Meltdown (2018) read those off-limits pages anyway, through the CPU's guesswork.
                  Linux answered with page-table isolation: a second directory without them, swapped
                  in on every system call, which made PCID tags matter.
        · source  Hansen 2017

   RECAP
     1. A program's address is its own number, not a real place in memory.
     2. Sticky notes, the TLB, are checked first; a miss means a four-level directory walk.
     3. The note made every later read in that page take one cycle.
     4. Program B's same address led through its own directory to a different room.
   TAKEAWAY  Each program's addresses go through its own directory, which only the operating system
             can set. So a program reaches only rooms it was given, and notes keep it fast.

━━ Story 3 of 3 · The page isn't in memory  (fault)  18 steps, 90 s at 1x
   what if   What if… the page was moved out to disk
   story     The page was moved out to disk: the CPU stops, the operating system fetches it back,
             and the read starts over.
   (steps 0–6 repeat story 1 and are skipped here; --full shows them)

   ▸ Chapter 3 of 5 · The directory
     about     On a miss, the CPU reads this program's directory, the page table: four small tables
               in a chain. Each 9 bits of the page number pick one line in one table.
     so far    No note has page `0x7f3a2c108`, so the notes can't say where it lives.
     now       Read the program's directory, one table after another.
     done when The last table's line names the page's room, or says it has none.
   7  Bits 29–21 pick line 352 of the third table, which leads to the last.   ‹walk.level›
        look      t2.e1
   8  ★ Line 264 of the last table says not present: the page isn't in memory.   ‹walk.absent›
        why       The line's present flag is 0, so it names no room for the CPU to use.
        look      t3.e1
        picture   a room whose boxes went to storage = a page out on disk: a page fault
        · how     Bit 0 of the line, P, is 0. The CPU then ignores every other bit, so the operating
                  system may keep its own notes there: here, the page's slot on disk.
        · real    Linux keeps the slot there too, but stored inverted (every bit flipped), so the
                  line can never look like a real frame number to a CPU that reads it by mistake
                  (the L1TF flaw, 2018). This run stores the slot plainly in bits 12 and up.
        · source  Linux pgtable_64.h __swp_entry

   ▸ Chapter 4 of 5 · Fetch from disk
     about     The page's contents went to storage: the operating system moved them to disk to free
               memory. This is a page fault: the CPU stops, and the operating system copies the page
               back. [page fault: The CPU finds a page is not in memory, stops, and asks the
               operating system to fetch it.]
     so far    The last table's line says page `0x7f3a2c108` is not in memory.
     now       Stop the program, and fetch the page back from disk.
     done when The directory line names a room again, marked present.
   9  The CPU stops the program and hands the address to the kernel: 3 000 cycles. [kernel: The
      core of the operating system: it hands out memory and fetches pages back from disk.]   ‹fault.trap›
        why       Only the operating system knows where the page went, so the CPU must ask it.
        look      kernel
        · cost    3 000 cycles, about 1 µs: saving the program's place, entering the kernel, finding
                  the line, and returning.
        · how     The CPU raises exception 14, a page fault, puts the address in register CR2 and
                  jumps to the kernel's handler. The read is undone, so it can run again from the
                  start.
        · code    `raise(PAGE_FAULT, va);` (line 11)
        · source  Intel SDM 2025, Vol. 3A, ch. 4, Paging
  10  ★ The kernel copies the page from disk slot `0x712` into free room `0x88e85`.   ‹fault.disk›
        why       This copy is the slow part: 60 000 cycles, longer than everything else in this
                  read together.
        look      page
        picture   a room whose boxes went to storage = a page out on disk: a page fault
        · cost    60 000 cycles at 3 GHz is 20 µs, a typical 4 KiB read from an NVMe SSD. The
                  counter adds them as this read's delay, but the program does no work then: it
                  sleeps, and the CPU runs another program until the disk is done.
        · how     The kernel takes a free room, asks the disk for the slot named in the line, and
                  waits for the copy to finish.
        · code    `swap_read(pte_to_swp_entry(*pte), frame);` (line 22)
        · edge    A fault that needs no disk, such as the first touch of fresh memory (a minor
                  fault), costs only the stop and the kernel's work: no copy, no wait.
        · real    An SSD read takes about 10–100 µs; a spinning disk takes milliseconds, millions of
                  cycles.
        · source  Gregg 2020, Table 2.2
  11  The kernel writes room `0x88e85` into line 264, marks it present, and returns.   ‹fault.fix›
        why       The read that stopped halfway can now start over from the beginning.
        look      t3.e1
        · how     The new line holds frame `0x88e85` with P set, plus RW, US, A, D and NX, the flags
                  of a data page.
        · code    `*pte = frame | PRESENT | RW | USER | ACCESSED | DIRTY | NX;` (line 23)
        · source  OSTEP 2023, ch. 21

   ▸ Chapter 5 of 5 · Try again
     about     The CPU runs the same read again from the start: note check, directory, room. The
               directory lines it needs were read moments ago.
     so far    The kernel fixed the directory line, but the read itself never finished.
     now       Run the same read again, from the start.
     done when The real address fills in, and the byte lights up.
     PREDICT  The read starts over. Will a sticky note have the page now?
              A) Yes: the kernel has put the page back in memory
                 → If you thought the notes learn what the kernel fixed: the kernel wrote the
                   directory line, not a note. A note is written only after a walk that ends in a
                   room, and the last one ended at “not present”. [m-note]
              B) No: no note was written, so it walks again   ✓
                 → Right. The last walk found no room, so it left no note, and the kernel only
                   changed the directory. The CPU walks again.
              why: The CPU writes a note only after a walk that finds the room, and the kernel fixed
                   the directory, not the notes.
  12  ★ Still no note for page `0x7f3a2c108`: a miss.   ‹retry.miss›
        why       A note is written only after a walk that finds a room, and the last walk didn't.
        look      tlb
        · how     The CPU never keeps a note of a not-present line, so turning P from 0 to 1 needs
                  no clearing of notes (SDM §4.10.2 and §4.10.4).
        · edge    Changing a line that was present is different: an old note may still hold it. The
                  kernel must drop it with `invlpg`, and on a many-core machine interrupt every core
                  that may hold it, a TLB shootdown.
        · source  Intel SDM 2025, Vol. 3A, ch. 4, Paging
  13  The same 4 lines again, now from the cache: 56 cycles in all. [cache: Small, fast memory
      beside the CPU that keeps copies of recently read memory, so reading again is cheap.]   ‹retry.walk›
        why       The first walk left these lines in fast memory beside the CPU, so each read is
                  cheap.
        look      t0, t1, t2, t3
        · cost    56 cycles for 4 reads, against 240 each from main memory.
        · how     The cache here models the CPU's second-level cache: about 14 cycles a read. The
                  kernel's own write of the last line left that line there too.
        · source  Drepper 2007, §3.3 and §4
  14  Room `0x88e85`, then offset `0xe48`: the physical address, `0x88e8_5e48`.   ‹retry.address›
        why       The offset copies over unchanged; only the room number came from the directory.
        look      pa
        picture   the real room = a frame of physical memory
        · how     The sum is the usual frame × 4,096 + offset; the frame is the room the kernel
                  filled from disk.
        · code    `return table | off;` (line 15)
  15  A sticky note now maps page `0x7f3a2c108` to room `0x88e85`, replacing `0x7f3a2c3e6`'s note.   ‹retry.fill›
        look      tlb.v0, tlb.p0
        · how     This is the note the first try could not write: its walk found “not present”, so
                  only the retry, ending in a room, leaves one.
  16  The byte at physical address `0x88e8_5e48` is `0x37`: 64 018 cycles for one byte.   ‹retry.byte›
        look      page.b1
  17  ★ A hit costs 1 cycle and a walk up to 961; this read cost 64 018.   ‹retry.cost›
        why       The disk made up 94% of it, which is why the system keeps busy pages in memory.
        look      ssd
        · cost    Of 64 018 cycles, 60 000 were the disk copy and 3 000 the stop and the kernel's
                  handler; the note checks and walks were the rest.
        · edge    The disk share is waiting, not CPU work: the program sleeps through it while
                  others run. A machine short of memory that faults constantly does little but wait,
                  which is called thrashing.
        · source  OSTEP 2023, ch. 21

   RECAP
     1. The directory said the page was out on disk: a page fault.
     2. The kernel copied it into a free room and fixed the directory line.
     3. The read started over, walked the directory again and found the room.
   TAKEAWAY  A page out on disk costs tens of thousands of cycles. That is why the operating system
             keeps busy pages in memory.
