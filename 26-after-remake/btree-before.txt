B+ tree: How a database finds one row without reading them all
level core · 3 stories · 4 knobs (Ids per page, How many ids, Your own ids (optional), Finish with a range search)

HOOK      A table of a million orders. How does a database find one order in three or four reads,
          instead of checking every row?
GOAL      Find any id among many by reading one page per level, and keep the tree that short as ids
          arrive.
OBJECTIVES
  o-descend: Predict how many pages a search reads from the tree's height, not from how many pages
             it has.
  o-split: Perform a split: say which ids stay, which move to the new page, and which id goes up.
  o-grow: Explain why the tree grows a new level at the top, so every bottom page stays equally
          deep.
  o-scan: Count the pages a range search reads: one per level going down, then one per page walked
          along.
  o-seq: Explain why ids that only grow leave half-full pages behind when every split is down the
         middle.
PICTURE   a library with signposts
  pile    books dropped in a pile, checked spine by spine  =  a table with no index  (index)
  shelf   a shelf holding a few books in order  =  a bottom page of the tree, a leaf  (leaf)
  signposta signpost saying which aisle to take  =  an upper page and its separators  (separator)
  door    the signpost at the door  =  the root, where every search starts  (root)
  walk    walking from the door to one shelf  =  the descent: one page read per level
  chain   shelves standing side by side  =  the leaf chain, each leaf linked to the next
  breaks  A library adds shelves at the end of an aisle. A full page here splits in two and sends a
          signpost up, so new levels appear at the top, by the door.
BELIEFS
  m-every: “To be sure it finds the id, a search has to look through every page.” Each signpost page
           sends the search to exactly one page below it, so it reads one page per level.
  m-bottom: “When the tree needs more room, it grows downward: new levels appear under the bottom
            pages.” Full pages split and send an id up; only a root split adds a level, and it adds
            it on top.
  m-grow: “A full page can stretch to hold one more id, or the new id gets a page of its own.” A
          page is a fixed-size block on disk, so a page with too many ids must split into two.
  m-back: “To reach the next ids in a range, the search climbs back up the tree, like in a binary
          search tree.” Each bottom page links to the next one, so the search walks sideways and
          never re-reads the pages above.
WORDS
  index: (a sorted guide) A sorted guide that says where each row is, like the tabs of a phone book.
  page: (a fixed-size block) A fixed-size block that the disk reads in one go; here it holds a few
        ids.
  root: (the top page) The top page of the tree, where every search starts.
  leaf: (a bottom page) A page at the bottom of the tree, holding the ids themselves.
  separator: (a signpost id) An id in an upper page that says which way to go: smaller ids go left.

                   before it can be saved. Each half then has room for later ids.

                  multiplies the ids within reach by the ids per page, so levels grow as log n:

                  memory, and a lookup that goes to disk reads only the lower levels there.

   ▸ Chapter 5 of 5 · Range scan
     about     To find every id from 33 to 75, go down once, to the first one. The leaves are linked
               left to right, like shelves side by side, so the search then walks along them.
     so far    Any one id is found by reading one page per level, but a range can hold many ids.
     now       Go down once to where 33 would be, then walk along the leaves.
     done when The search moves sideways from leaf to leaf, and stops once it passes 75 or runs out
               of leaves.
  16  Find ids 33 to 75: going down p3 → p4 reads 2 pages.   ‹scan.descend›
        why       Going down only finds where the range starts; the rest lies to the right, in
                  order.
        look      p3, p4
     PREDICT  p4 is used up, and the range goes on. How does the search reach the next ids?
              A) It walks along to the next leaf   ✓
                 → Right. p4 links to p5, so the next read is the very next leaf, and no page above
                   is read again.
              B) It climbs back up to the page above
                 → If you thought it climbs back up, as in a binary search tree: p4 keeps a link to
                   p5, so the search walks sideways. Climbing would re-read a page it has already
                   read. [m-back]
              C) It starts again from the root
                 → If you thought it starts over: that would re-read every page on the way down,
                   once per leaf. The link from p4 to p5 skips all of that. [m-back]
              why: Each leaf keeps a link to the next one, so the search walks sideways and never
                   re-reads the pages above.
  17  Walk on to p5: 3 ids in range, none past 75.   ‹scan.walk›
        why       Each leaf keeps a link to the next one, so the search never climbs back up.
        look      ln-p4-p5, p5
        picture   shelves standing side by side = the leaf chain, each leaf linked to the next
        · how     The search reads each leaf's ids in order and stops at the first id past 75, or
                  when there is no next leaf.
        · code    `leaf = leaf.next # sideways, never back up` (line 33)
        · real    The link matters beyond ranges. In Lehman and Yao's design, which PostgreSQL
                  follows, a reader that reaches a page someone just split moves right along the
                  link and still finds its id, without locking the path.
        · source  Lehman & Yao 1981; PostgreSQL 2024
  18  Walk on to p2: 0 ids in range. 80 is past 75, so the search stops.   ‹scan.stop›
        why       The leaves are in order, so every id after 80 is past 75 too.
        look      ln-p5-p2, p2
  19  ★ 5 ids found with 4 page reads: 2 going down, 2 along.   ‹scan.done›
        why       The way down is paid once; every further read is one more leaf of the range.
        look      k33, k35, k51, k61, k75
        · cost    4 reads = 2 levels down + 2 leaves walked. A range costs the height plus the
                  leaves it spans, however many ids lie outside it.
        · real    PostgreSQL links each level's pages both ways, so a descending range (ORDER BY id
                  DESC) walks the same chain to the left.
        · source  PostgreSQL 2024; PostgreSQL 2024

   RECAP
     1. Without an index, finding one id meant checking them one by one.
     2. The tree keeps ids sorted in pages; a full page splits in two.
     3. Signposts in the upper pages lead each search down, one page per level.
     4. The bottom pages are linked, so a range is a walk along them.
   TAKEAWAY  A B+ tree finds any id by reading one page per level, and stays shallow because full
             pages split and it grows at the top.
   CAN NOW   o-descend, o-split, o-grow, o-scan, o-seq

     about     A signpost page that is over-full splits too, and its middle id moves up, out of it.
               When the root splits, a new root appears on top: the tree grows at the top, never at
               the bottom.

     now       Split the top page too, and send its middle id up into a new root.
     done when A new root sits on top, and every leaf is still on the bottom row.
     PREDICT  p3 is the top page, and it is over-full too. Where does the tree get its new level?
              A) At the bottom: the leaves go a level deeper
                 → If you thought trees grow downward: a level under some leaves would leave the
                   others shallower. Instead p3 splits and a new root, p8, appears above it.
                   [m-bottom]

                   moves down together.
              C) Nowhere: p3 just keeps 4 ids

               the bottom.
