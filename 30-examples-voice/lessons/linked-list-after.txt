Linked list: Items that point to the next one, so inserting moves nothing
level intro · 3 stories · 2 knobs (List length, Insert after item)

HOOK      Putting a number in the middle of an array means sliding everything after it over. Can we
          insert without moving anything?
GOAL      Insert into the middle of a list without moving anything.
OBJECTIVES
  o-shift: Explain why inserting into an array moves items and inserting into a linked list does
           not. (insert, wrong)
  o-order: Do the two pointer writes of an insert in the right order, and say why the order matters.
           (insert, wrong)
  o-cost: Say what a linked list pays instead: a walk from head, an extra address and an allocation
          per node. (insert, find)
PICTURE   a treasure hunt
  node    a clue card  =  a node  (node)
  value   the prize written on the card  =  its value
  next    where the next clue is hidden  =  next, an address  (pointer)
  head    the first clue, handed to you  =  head  (head)
  null    “this is the last clue”  =  null  (null)
  breaks  A hiding place here is a number, and if you knew it you could jump straight there. The
          catch is that only the clue before it knows the number.
BELIEFS
  m-prevfirst: “You point the old node at the new one first, then fill in the new node.” The old
               node's `next` is the only copy of the next address. Overwrite it first and the rest
               of the list is gone.
  m-order: “The two writes don't touch each other, so either order works.” One write reads the old
           node's `next`, the other overwrites it. The read has to come first.
  m-jump: “A linked list is an array with arrows drawn on it, so you can jump to item 5.” A node's
          address is written only in the node before it, so you have to walk there.
  m-count: “Reaching the 5th item takes 5 arrows, one per item.” You start standing on the 1st node,
           so 4 arrows reach the 5th.
  m-copy: “Copying a node's `next` copies the address it held earlier.” A copy takes what the field
          holds right now.
  m-empty: “Overwriting an arrow leaves it empty, so a copy of it reads null.” An overwrite puts a
           new address in its place. Null appears only where null is written.
WORDS
  address: (a house number for memory) The number that says where something is stored in memory,
           like a house number.
  node: (a box) One item of a linked list, holding a value and the address of the next box.
  pointer: (an arrow) A value that holds a memory address, so it says where something else lives.
  head: (the first arrow) A variable holding the address of the first box. Every trip starts there.
  null: (no address) A special value meaning “no address”. In next, it means nothing comes after.

        why       48's address is now written in two places, so changing 12 is safe.
        look      nx.next, nx->n2
        picture   where the next clue is hidden = next, an address
        · cost    Once you stand on 12 this is O(1), two writes whatever the length. Getting to 12
                  was the O(k) part.
        · how     `new.next = prev.next` must run first, because until it does, 12's `next` is the
                  only copy of 48's address.
        · code    `new.next = prev.next` (line 14)
        · real    Linux's lists are doubly linked. Its __list_add sets next->prev, fills in
                  new->next and new->prev, and writes prev->next last.
        · source  Linux list.h __list_add
  14  ★ 12's `next` now points at 42. The chain runs 12 → 42 → 48.   ‹insert.link-prev›
        why       That single write is enough, because every walk from head now passes through 42.
        look      n1.next, n1->nx
        · how     Storing one aligned address is a single write on common CPUs, so a reader sees the
                  old list or the new one, never half of each.
        · code    `prev.next = new` (line 15)
        · edge    A doubly linked list needs four writes, and the same rule holds: finish the new
                  node before anything points at it.
        · real    With readers running at the same time, this last write is the “publish”. Linux's
                  RCU lists set new->next and new->prev, then rcu_assign_pointer(prev->next, new).

        · source  Linux rculist.h __list_add_rcu; Harris 2001

        why       This is the check that matters. A walk along the arrows now meets 42 in its place.
        look      head
        · how     Every old node still sits at the address on its label. Nothing was copied, and
                  only 12's `next` changed.
        · edge    Because nothing moved, any other variable still pointing at a node stays valid. An
                  array insert can't promise that, because growing copies the block to a new
                  address.

     about     Each one is quick at something different. An array has to slide items to make room. A
               linked list only changes two arrows, but it must walk from head to find the spot.
     so far    Both now hold 42 right after 12, but each paid a different price.
     now       Line up the two costs.
     done when You can say what each cost grows with.
  16  ★ The array moved 3 items. The list moved none, changed 2 arrows and followed 1 arrow.   ‹tradeoff.insert›
        why       Neither one is free. The array pays for every item after the gap, and the list
                  pays for every item before it.
        look      arr, n1
        · cost    At position k of n, the array finds the spot in O(1) and shifts n − k items, while
                  the list walks k − 1 arrows and splices in O(1). The list also stores an extra
                  address in every node and makes one allocation per node.
        · edge    Measured, the array can win anyway. Stroustrup inserted random numbers into a
                  sorted sequence and then removed them at random spots, and a C++ vector still beat
                  a linked list with 500,000 numbers. Finding each spot walks the list, with a cache
                  miss on every hop.
        · real    Lists earn their place when you already hold the node. CPython's lru_cache keeps a
                  doubly linked list, so a hit moves to the front with a few pointer writes and no
                  walk.
        · source  Stroustrup 2012 Figure 1; CPython functools.py lru_cache

   RECAP
     1. The array had to slide every later item over to make room.
     2. A node holds a value and `next`, the address of the next node.
     3. Inserting changed two arrows, in the right order. Nothing moved.
     4. Reaching the spot meant following arrows from head, one at a time.
   TAKEAWAY  A linked list never moves its items, because an insert only changes two arrows. It pays
             for that with a walk from head and an extra address in every node.

  12  Make `new`, a node for 42, wherever memory has room. Its `next` is null.   ‹insert.make›
        why       No arrow leads to it yet, so a walk from head can't reach it.
        look      nx
        · how     In this run it landed at `0x7f3a_5a30`, but any free spot would do, and that is
                  the whole point.
        · code    `new = Node(value)` (line 13)
        · edge    In C, malloc can fail and return NULL. Real code checks before linking the node
                  in.
  13  ★ First, 12's `next` is pointed at 42.   ‹wrong.prev-first›
        why       That was the only place 48's address was written, and now it has been written
                  over.
        look      n1.next
        picture   where the next clue is hidden = next, an address
        · how     Overwriting a pointer you still need is the classic linked-list bug, which is why
                  textbooks write the two lines in a fixed order.
        · code    `prev.next = new` ran before `new.next = prev.next`.
        · edge    Python's tuple assignment is safe in either order, because `prev.next, new.next =
                  new, prev.next` reads the whole right side before writing anything.
        · source  Python reference §7.2
     PREDICT  Next, 42 copies 12's `next` (`new.next = prev.next`). Where will 42's `next` point?
              A) At 48
                 → That is what 12's `next` held until one step ago. The copy reads what is there
                   now, which is 42's own address. [m-copy]
              B) At 42 itself   ✓
                 → Yes. 12's `next` now holds 42's own address, so copying it makes 42 point at
                   itself.
              C) Nowhere: null
                 → An overwrite doesn't leave a field empty. It put 42's own address, `0x7f3a_5a30`,
                   into 12's `next`, and that is what gets copied. [m-empty]
              why: 12's next now holds 42's own address, so copying it makes 42 point at itself.
  14  ★ 42's `next` copies 12's, which is now 42's own address, so 42 points at itself.   ‹wrong.self-loop›
        why       12's `next` already held 42's address, and a copy takes what is there now.
        look      nx.next
        · how     An assignment reads its right side at the moment it runs. Nothing remembers what
                  12's `next` held before.
        · code    `new.next = prev.next` (line 14): now `0x7f3a_5a30`, 42's own address.
  15  ★ Nothing points at 48 now, so 3 nodes are lost for good: 48, 17 and 23.   ‹wrong.lost›
        why       Each of those addresses was written only in the node before it, and nothing else
                  remembers them.
        look      lost
        · how     In C, lost nodes leak: still allocated, but no pointer is left to free them with.
                  In CPython, reference counts drop to zero when 12's `next` is overwritten, so they
                  are freed at once. Either way the data is gone.
        · real    Valgrind calls the first lost block “definitely lost” and any behind it
                  “indirectly lost”, meaning they are pointed to only from lost blocks.
        · source  Valgrind Memcheck manual
  16  Reading from head gives 31 → 12 → 42 → 42 → … and never reaches the end.   ‹wrong.read-loop›
        why       A program walking this list would hang here, going round and round the same node.
        look      nx
        · how     The walk waits for null, and the loop never reaches one. Floyd's “tortoise and
                  hare” spots a loop with two markers: one moves 1 arrow a step, the other 2, and
                  they meet only if there is a loop.
        · source  Knuth 1997, Vol. 2, §3.1, exercise 6

     about     Now swap the two writes. The new node copies 12's `next` first, which saves 48's
               address, and only then does 12 point at the new node.
     so far    Changing 12 first lost 3 nodes, and the walk never ends.
     now       Rewind, and do the two writes in the other order.
     done when 48's address is in two places before 12 changes, and nothing is lost.
  17  We rewind to before the mistake, when 12 still points at 48.   ‹right.rewind›
        why       It is the same list and the same new node, and only the order of the two writes
                  changes.
        look      n1->n2
        · how     42 is back at `0x7f3a_5a30` with `next` null, and nothing points at it yet.
  18  ★ First, 42's `next` copies 12's. 48's address is now in two places.   ‹right.save-next›
        why       That copy is the safety net, so 12 can now change without losing 48.
        look      nx.next, nx->n2
        · cost    It is still 2 writes, so the right order costs nothing extra.
        · code    `new.next = prev.next` (line 14), before `prev.next = new`.
  19  Then 12 points at 42, and every node can still be reached.   ‹right.link-prev›
        look      n1->nx
        · code    `prev.next = new` (line 15)
  20  Reading from head gives 31 → 12 → 42 → 48 → 17 → 23, with 42 in its place.   ‹right.read›
        look      head
        · how     The walk ends at null again, with no loop and no node lost.

   RECAP
     1. Changing the old arrow first erased the only copy of the next address.
     2. The new node then pointed at itself, and the rest of the list was lost.
     3. In the right order the new node saves the address first, and nothing is lost.
   TAKEAWAY  Before you overwrite an arrow, save where it pointed. Point the new node onward first,
             and only then point the old node at it.
