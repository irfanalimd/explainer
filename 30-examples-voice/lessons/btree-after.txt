B+ tree: How a database finds one row without reading them all
level core · 3 stories · 4 knobs (Ids per page, How many ids, Your own ids (optional), Finish with a range search)

HOOK      Picture a table with a million orders. How does a database find one in three or four
          reads, without checking every row?
GOAL      Find any id among many by reading one page per level, and keep the tree that short as ids
          arrive.
OBJECTIVES
  o-descend: Predict how many pages a search reads from the tree's height, not from how many pages
             it has.
  o-split: Perform a split: say which ids stay, which move to the new page, and which id goes up.
  o-grow: Explain why the tree grows a new level at the top, so every bottom page stays equally
          deep. (sequential, rootsplit)
  o-scan: Count the pages a range search reads: one per level going down, then one per page walked
          along.
  o-seq: Explain why ids that only grow leave half-full pages behind when every split is down the
         middle. (sequential)
PICTURE   a library with signposts
  pile    books dropped in a pile, checked spine by spine  =  a table with no index  (index)
  shelf   a shelf holding a few books in order  =  a bottom page of the tree, a leaf  (leaf)
  signposta signpost saying which aisle to take  =  an upper page and its separators  (separator)
  door    the signpost at the door  =  the root, where every search starts  (root)
  walk    walking from the door to one shelf  =  the descent: one page read per level
  chain   shelves standing side by side  =  the leaf chain, each leaf linked to the next
  breaks  A library makes room by adding shelves at the end of an aisle. Here a full page splits in
          two and sends a signpost up instead, so new levels appear at the top, by the door.
BELIEFS
  m-every: “To be sure it finds the id, a search has to look through every page.” Each signpost page
           sends the search to exactly one page below it, so the search reads one page per level and
           skips the rest.
  m-bottom: “When the tree needs more room, it grows downward: new levels appear under the bottom
            pages.” Full pages split and send an id up to the page above. Only a split of the root
            adds a level, and the new level goes on top.
  m-grow: “A full page can stretch to hold one more id, or the new id gets a page of its own.” A
          page is a fixed-size block on disk, so a page with one id too many has to split into two.
  m-back: “To reach the next ids in a range, the search climbs back up the tree, like in a binary
          search tree.” Each bottom page links to the next one, so the search walks sideways and
          never reads the pages above it again.
WORDS
  index: (a sorted guide) A sorted guide that says where each row is, like the tabs of a phone book.
  page: (a fixed-size block) A fixed-size block that the disk reads in one go. Here each one holds a
        few ids.
  root: (the top page) The top page of the tree, where every search starts.
  leaf: (a bottom page) A page at the bottom of the tree, holding the ids themselves.
  separator: (a signpost id) An id in an upper page that tells a search which way to go. Smaller ids
             go to its left.
NUMBERS   levels * · pages · pages read · pages split in two * · how full the bottom pages are * · ids checked one by one   (* in each pause's recap)

     about     When a leaf gets one id too many, it splits in two. The first id of the right half is

               they are made. [leaf: A page at the bottom of the tree, holding the ids themselves.]

     done when Two half-full leaves sit side by side under a new top page.
     PREDICT  Page p1 now holds 4 ids, but a page only fits 3. What happens to it?
              A) It splits into two half-full pages   ✓
                 → Right. A page is a fixed-size block, so p1 splits. It keeps 2 ids, and 80 and 88
                   move to p2.
              B) The new id gets a page of its own
                 → Giving the newcomer a page of its own sounds tidy, but pages would sit nearly
                   empty and every search would have more of them to read. Instead p1 splits, and both
                   halves keep room to spare. [m-grow]
              C) The page grows to fit 4
                 → A page can't stretch, because it is a fixed-size block on disk with room for 3.
                   So p1 splits, keeping 2 ids and moving 80 and 88 to p2. [m-grow]
              why: A page has a fixed size on disk, and 4 ids don't fit in it, so p1 has to split
                   before it can be saved. Each half then has room for the ids that come later.

     about     From now on, each insert starts at the root. It follows the signposts down, one page
               per level, to the leaf where its id belongs.
     so far    Splitting put signposts above the leaves, so the tree now has 3 pages on 2 levels.
     now       Follow the signposts from the root down to the one leaf for 15.
     done when Each insert lights one page per level, 2 here, out of 3 pages.
     PREDICT  The id 15 is next. How many pages must the search read to find the leaf it belongs in?
              A) 2: one page per level   ✓
                 → Right. The search reads p3 → p1, which is 2 pages, one per level, because each
                   signpost page points to only one page below it.
              B) All 3 pages, to be sure
                 → Checking everything feels safer, but the signposts already rule the other pages
                   out. Each one points to a single page below it, so the search reads 2 of the 3
                   pages. A real tree of billions of rows reads about 4. [m-every]
              C) Only 1: it goes straight to a leaf
                 → The search can't jump straight to a leaf, because it doesn't know which leaf yet.
                   It starts at the root, the only page it can find on its own, and reads one page per
                   level, 2 in all.
              why: Each signpost page points to exactly one page below it, so the search reads one
                   page per level, which is 2 here.
   7  ★ The id 15 goes down p3 → p1, testing `15 < 80`.   ‹descend.insert›
        why       Look at how little of the tree lights up. The separators in each page rule out
                  every page below it except one, so only 2 pages are read.
        look      p3, p1
        picture   walking from the door to one shelf = the descent: one page read per level
        · cost    2 page reads, one per level, however many pages the tree holds. Each level
                  multiplies the ids within reach by the ids per page, so the number of levels, and
                  of reads, grows as O(log n).
        · how     At each page the search counts the separators that are ≤ the id and takes that
                  child (Python's bisect_right). So an id equal to a separator goes right, to the
                  leaf where that id itself lives.
        · code    `node = node.kids[bisect_right(node.keys, key)]` (line 5)
        · real    An 8 KB page holds a few hundred separators, so 3 levels reach tens of millions of
                  rows and 4 reach billions. Every lookup reads the top levels, so they stay in
                  memory, and a lookup that goes to disk reads only the lower levels there.
        · source  PostgreSQL docs, page layout; Comer 1979

   ▸ Chapter 5 of 5 · Range scan
     about     To find every id from 33 to 75, the search goes down once, to where 33 would be. The
               leaves are linked left to right, like shelves standing side by side, so from there it
               walks along them.
     so far    Any one id is found by reading one page per level, but a range can hold many ids.
     now       Go down once to where 33 would be, then walk along the leaves.
     done when The search moves sideways from leaf to leaf, and stops once it passes 75 or runs out
               of leaves.
  16  To find ids 33 to 75, the search goes down p3 → p4, reading 2 pages.   ‹scan.descend›
        why       Going down only finds where the range starts. Everything else in it lies to the
                  right, already in order.
        look      p3, p4
     PREDICT  The search has read everything in p4, and the range goes on. How does it reach the
              next ids?
              A) It walks along to the next leaf   ✓
                 → Right. Page p4 links to p5, so the next read is the very next leaf, and no page
                   above it is read again.
              B) It climbs back up to the page above
                 → That is how you would move on in a binary search tree, which has no links between
                   its leaves. Here p4 keeps a link to p5, so the search walks sideways, and climbing
                   would only re-read a page it has already read. [m-back]
              C) It starts again from the root
                 → Starting over would work, but it would re-read every page on the way down, once
                   for each leaf. The link from p4 to p5 skips all of that. [m-back]
              why: Each leaf keeps a link to the one after it, so the search walks sideways and
                   never reads the pages above it again.
  17  The search walks on to p5, which has 3 ids in range and none past 75.   ‹scan.walk›
        why       Each leaf keeps a link to the one after it, so the search moves sideways and never
                  climbs back up.
        look      ln-p4-p5, p5
        picture   shelves standing side by side = the leaf chain, each leaf linked to the next
        · how     The search reads each leaf's ids in order and stops at the first id past 75, or
                  when there is no next leaf.
        · code    `leaf = leaf.next # sideways, never back up` (line 33)
        · real    The link matters beyond ranges. In Lehman and Yao's design, which PostgreSQL
                  follows, a reader that reaches a page someone has just split moves right along the
                  link and still finds its id, without locking the path.
        · source  Lehman & Yao 1981; PostgreSQL nbtree README
  18  In p2 it finds 0 ids in range, then meets 80, which is past 75, so it stops.   ‹scan.stop›
        why       The leaves are in order, so every id after 80 is past 75 as well, and there is
                  nothing left worth reading.
        look      ln-p5-p2, p2
  19  ★ The search found 5 ids in 4 page reads, 2 down and 2 along the leaves.   ‹scan.done›
        why       The trip down is paid once. After that, each extra read is one more leaf of the
                  range.
        look      k33, k35, k51, k61, k75
        · cost    4 reads = 2 levels down + 2 leaves walked. A range costs the height plus the
                  leaves it spans, however many ids lie outside it.
        · real    PostgreSQL links each level's pages both ways, so a descending range (ORDER BY id
                  DESC) walks the same chain to the left.
        · source  PostgreSQL docs, B-tree structure; PostgreSQL nbtree README

   RECAP
     1. Without an index, finding one id meant checking them one by one.
     2. The tree keeps its ids sorted in pages, and a full page splits in two.
     3. Signposts in the upper pages lead each search down, one page per level.
     4. The bottom pages are linked, so a range search walks along them.
   TAKEAWAY  A B+ tree finds any id by reading one page per level. It stays shallow because full
             pages split, and the only new level it ever adds goes on top.
   CAN NOW   o-descend, o-split, o-scan
