MapReduce: Counting words with a team of machines
level core · 4 stories · 4 knobs (Reading machines, Counting machines, Add up repeats first, Text to count)

HOOK      Each machine reads only part of the text. How do they still count every word exactly, none
          missed or counted twice?
GOAL      Count every word of a text exactly, with machines that each read only part of it.
OBJECTIVES
  o-split: Say why the text is cut into pieces and read in parallel, and what that buys. (happy,
           skew)
  o-hash: Explain why every copy of a word must reach the same counter, and how a hash does it
          without asking anyone.
  o-reduce: Say what a counting machine writes: one total for each different word it holds. (happy)
  o-crash: Say why a crashed reading task can simply run again, even one that had finished. (crash)
  o-slow: Say why a backup copy of a slow piece is safe, and why only one copy's slips may count.
          (straggler)
  o-skew: Explain why one very common word overloads one counter, and why adding up repeats early
          helps where more machines or a backup don't. (skew)
PICTURE   a library counted by a team
  master  the coordinator handing out shelves  =  the master  (master)
  split   one shelf of books  =  one piece of the text (a split)  (split)
  mapper  a helper tallying their shelf  =  a reading machine (a mapper)  (mapper)
  slip    a tally slip “fox: 1”  =  a record `(fox, 1)`: the word, and the number 1
  hash    “all slips for one word go to one person”  =  a fixed rule on the word's letters (a hash) that picks one counting machine  (hash)
  reducer the person adding them up  =  a counting machine (a reducer)  (reducer)
  output  the noticeboard  =  the output: a folder with one file per counting machine
  breaks  Helpers would talk to agree who counts which word. Machines never talk about it: each one
          runs the same rule on the word and gets the same answer.
BELIEFS
  m-central: “Each machine counts its piece, and one machine adds it all up at the end.” Then one
             machine would add up every slip. Instead each word's slips meet on one counter, so the
             adding is shared too.
  m-even: “Spreading the slips evenly over the counters is best.” Copies of one word would land on
          different counters, and none could give its full count.
  m-one: “A counting machine adds all its slips into one number.” It adds each word's slips apart
         from the rest: one total for each different word it holds.
  m-lost: “A crashed machine's words are lost, so the count comes out short.” Its piece is still in
          the input. Reading it again gives the same slips.
  m-restart: “One failure restarts the whole job.” Only the failed machine's tasks run again.
  m-done: “A reading task that had finished is safe when its machine dies later.” Its slips were on
          that machine's own disk, so they die with it, and the piece is read again.
  m-wait: “The job has to wait for its slowest machine.” A backup copy of the slow piece on a free
          machine gives the same slips. The first copy to finish wins.
  m-skip: “Skipping a slow piece is a fair price for finishing on time.” Its words would never be
          counted. MapReduce never trades a correct count for speed.
  m-both: “Keeping both copies' slips is harmless: the extra copy is only a spare.” Both copies
          wrote slips for the same words, so keeping both counts those words twice.
  m-more: “More counting machines would spread out one very common word.” The hash sends every copy
          of a word to one counter, however many there are. More machines only move other words.
  m-backup: “A backup copy shares out a busy machine's work.” A backup does the same work again from
            the same input. It beats a slow machine, not a big pile of work.
  m-readers: “More reading machines would share out a common word's slips.” The counter is picked
             from the word alone, so every copy still goes to the same counter however many machines
             read.
  m-combine: “Adding up repeats early changes the counts.” Each early slip carries its count, and
             the counter adds those counts, so the total is the same.
WORDS
  master: (the coordinator) The machine that hands out pieces of work, keeps track of them, and
          notices when a machine fails.
  split: (one piece of the text) One piece of the input, read by one machine, like one shelf of a
         library.
  mapper: (a reading machine) A machine running map: it reads one piece and writes a slip like (fox,
          1) for every word.
  hash: (a word's fixed number) A function that turns a word into a big number. The same word always
        gives the same number.
  shuffle: (sending each slip to its counter) The step where every slip travels to the machine that
           adds up its word.
  reducer: (a counting machine) A machine running reduce: it adds up all the slips for its share of
           the words.
  straggler: (a slow machine) A machine much slower than the rest, so everyone ends up waiting for
             it.
  combiner: (adding up early) Code that adds up repeats on the reading machine itself, before any
            slip is sent.
NUMBERS   words read * · sent between machines * · busiest counter's load * · tasks finished   (* in the dock)

   6  ★ the goes to reduce 0: its hash, 3 020 861 980, divided by 2 leaves remainder 0.   ‹shuffle.first›
        why       Dealt out in turn, a word's slips would land on several counters, and counters
                  never compare notes.
        look      m0.s0.w0, r0
        picture   “all slips for one word go to one person” = a fixed rule on the word's letters (a
                  hash) that picks one counting machine
        · how     Each mapper has already divided its slips into 2 regions, one per reduce task, and
                  each counter fetches its region from every mapper. The fetching starts early: the
                  master passes on each finished map's file locations as they come (§3.2). Only the
                  final sort and the adding wait for the last map, which might still hold a slip
                  they need (Hadoop sorts each map's slips on the map side and merges the sorted
                  runs as they arrive).
        · cost    In this model 85 bytes cross the network: each slip's word plus a 4-byte count
                  (real formats add length headers, and a reader on the counter's own machine sends
                  nothing). In the paper's clusters, network bandwidth was the scarce resource
                  (§3.4).
        · edge    Python's own hash() of a string changes from process to process (hash
                  randomization) unless PYTHONHASHSEED is fixed, and can differ between Python
                  versions, so two machines could disagree. Real jobs use a specified hash; this run
                  uses FNV-1a.
        · real    `hash(key) mod R` is only the paper's default partitioning function. A job can
                  supply its own: `hash(Hostname(urlkey)) mod R` puts every page of one website in
                  the same output file (§4.1). Within one counter, keys are handed to reduce in
                  increasing order, which is why each output file comes out sorted (§4.2).
        · code    `hash(word) % R` (lines 8–9)
        · source  J. Dean and S. Ghemawat, MapReduce: Simplified Data Processing on Large Clusters,

   6  ★ 200 goes to reduce 0: its hash, 3 286 718 301, divided by 3 leaves remainder 0.   ‹shuffle.first›
        why       Dealt out in turn, a code's slips would land on several counters, and counters
                  never compare notes.
        look      m0.s0.w0, r0
        picture   “all slips for one word go to one person” = a fixed rule on the word's letters (a
                  hash) that picks one counting machine
        · how     Each mapper has already divided its slips into 3 regions, one per reduce task, and
                  each counter fetches its region from every mapper. The fetching starts early: the
                  master passes on each finished map's file locations as they come (§3.2). Only the
                  final sort and the adding wait for the last map, which might still hold a slip
                  they need (Hadoop sorts each map's slips on the map side and merges the sorted
                  runs as they arrive).
        · cost    In this model 98 bytes cross the network: each slip's word plus a 4-byte count
                  (real formats add length headers, and a reader on the counter's own machine sends
                  nothing). In the paper's clusters, network bandwidth was the scarce resource
                  (§3.4).

                  randomization) unless PYTHONHASHSEED is fixed, and can differ between Python
                  versions, so two machines could disagree. Real jobs use a specified hash; this run
                  uses FNV-1a.

                  supply its own: `hash(Hostname(urlkey)) mod R` puts every page of one website in

                  increasing order, which is why each output file comes out sorted (§4.2).

     about     Each counter posts its totals to the shared output, like a list on a noticeboard.

  25  reduce 0 writes its 3 totals to the output.   ‹output.write›
        why       The output is a folder with one file per reduce task (here, per counter); this is
                  part-r-00000.
        look      output
        picture   the noticeboard = the output: a folder with one file per counting machine
        · how     Reduce output goes to the shared file system, so a finished reduce never runs
                  again, even if its machine dies later. If one reduce task does run twice (a backup
                  or a re-run), each copy writes a private temporary file, then atomically renames
                  it to the final name: exactly one copy's file survives (§3.3). That needs a file
                  system whose rename is atomic: Hadoop lets only one attempt of each task commit,
                  through an output committer (atomic with the v1 algorithm on HDFS; v2 trades that
                  for speed), and on object stores without an atomic rename, like S3, it needs
                  special committers.
        · edge    The name part-r-00000 is Hadoop's convention. In the paper the user names the
                  files: its word-count program writes /gfs/test/freq-00000-of-00100 and so on
                  (§3.1, Appendix A).

        look      r0
        · real    Real data is like this: word frequencies follow Zipf's law, so a few keys, like

     PREDICT  reduce 0 did the adding for 12 of the 14 slips. Which change takes most of that work
              off it, and keeps every count exact?
              A) Add a fourth counting machine
                 → With 4 counters every code is dealt again, but all of 200's slips still land

  28  ★ With 4 counters, every 200 would still go to one: 11 of 14 slips, 10 of them 200.   ‹skew.more›
        why       More counters spread out different codes, never the copies of one code: those must
                  meet to be counted.
        look      r0
        · cost    This line runs the run's own hash with one more counter: `hash(200) % 4 = 1`. A
                  counter's share of a key is all of it or none of it, so the busiest counter gets
                  at least 10 of the 14 slips whatever the count of counters.
        · edge    The partitioning function sees only the key (§4.1), so every value of a key goes
                  to one reduce task, which gets them in one call (§2). The fix has to shrink the
                  key's data before the shuffle, or rename the key.
        · source  J. Dean and S. Ghemawat, MapReduce: Simplified Data Processing on Large Clusters,
                  OSDI 2004, https://research.google/pubs/pub62/
  29  ★ If each reader ran a combiner first, 7 slips would travel, 5 to reduce 0. [combiner: Code
      that adds up repeats on the reading machine itself, before any slip is sent.]   ‹skew.combine›
        why       map 0's 4 slips for 200 would travel as one slip, `(200, 4)`: fewer slips to add,
                  the same total.
        look      r0
        · cost    After combining, reduce 0 still gets one slip per reader for each code it owns: 5
                  here, not 1. The gain is how often a code repeats inside one piece; at the paper's
                  M = 200,000 map tasks, one hot key can still bring about one slip per map task,
                  some 200,000, to one counter (§3.5); in Hadoop more, when a map's spills are not
                  all combined.
        · how     Turn on “Add up repeats first” to watch each reader do it. The paper suggests a
                  combiner where reduce is commutative and associative, as a sum is: order and
                  grouping don't change the result (§4.3). Its output must be the same kind of
                  (word, count) slip that reduce takes. An average, say, must travel as (sum, count)
                  pairs: an average of averages is wrong.
        · edge    Hadoop treats the combiner as an optimisation it may run zero, one or many times
                  on a map's output, so it must never change the answer. And a combiner helps only
                  when partial results merge: a reduce that needs every value at once (a median, a
                  sorted list) still sends the hot key's whole list to one machine. “Salting” adds a
                  suffix to the hot key so its slips spread over several counters, and a second job
                  merges the parts. That works when the parts merge (sums, counts, sorted runs); a
                  true median needs another second step, such as a histogram or range partitioning
                  on the value. The suffix must be deterministic, so a re-run task sends each line
                  where the first run did.
        · real    Spark's reduceByKey adds up on each reader first, like a combiner; groupByKey
                  ships every value, and Spark's guide warns to prefer reduceByKey or aggregateByKey
                  for sums and averages.
        · source  J. Dean and S. Ghemawat, MapReduce: Simplified Data Processing on Large Clusters,
                  OSDI 2004, https://research.google/pubs/pub62/; T. White, Hadoop: The Definitive
                  Guide, 4th ed., O'Reilly 2015, ch. 2, “Combiner Functions”; Apache Spark, RDD
                  Programming Guide, https://spark.apache.org/docs/latest/rdd-programming-guide.html
